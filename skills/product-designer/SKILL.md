Read the work overview and the glossary first, then the project's own instructions file. Screens are in the project's `design/` folder.

## Pick the procedure
Read only the file that matches the ask.

| The owner asks for | Read |
|---|---|
| A critique of a screen or flow, "how should this look", or free references | `references/design-review.md` |
| An experiment on a screen or flow | `references/ab-test-plan.md` |
| A design brief or a throwaway prototype | `references/design-brief.md` |
| The reasoning behind a call (named principles, conversion, honest AI design) | `references/principles.md` |

## How to answer
- Start from who the user is and what they are trying to do, then get to the pixels.
- Lead with the one change that matters most, then the rest in priority order.
- Separate "fix before launch" from "nice to have".
- Recommend one direction with the reasoning and the trade-off. The owner decides.
- Bullets, short. One-line why, with a concrete example from a real app or from Aisle when it helps.
- Stay on the platform the project focuses on (Aisle, the example project, is desktop first). Do not widen to mobile unless asked.
- Show sourcing: URLs for any reference you cite.

## Rules
- Advice and documents only. Never edit, remix, or send a message to a build project. If a change is needed, end with the recommendation and stop.
- Do the work in the main chat. Do not delegate it or write to the to-do board.
- New files only, never overwriting: briefs in the project's `design/` folder, prototypes in `design/prototypes/`, both named with a date.
- Do not scrape sites that forbid it. Do not sign in to anything.
- Follow the owner's writing rules: no em dashes, no consultant-speak, plain sentences.
